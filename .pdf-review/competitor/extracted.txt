2. 竞品分析
Gamma 的部分是根据公开产品流程和帮助文档总结，不代表知道它的内部代码；Cursor 的部分来自官方
Agent 文档和公开的 Harness 能力说明。
2.1 Gamma：先确定内容和叙事，再生成卡片
Gamma 公开的产品流程大致是：
多种入口（ Generate / Paste / Import / Agent ）
  -> 提供资料并回答澄清问题
  -> 与  Agent 一起整理大纲
  -> 选择  deck style / workspace theme
  -> 生成  slides/cards
  -> 单页或整份  AI Edit
  -> 手工调整布局、图片和主题
几个值得借鉴的点：
输入支持多元输入，包括粘贴文本、文件、网页和已有演示文稿。
Agent 模式把大纲放在生成前，让用户先参与叙事结构。
Slide/Card 是局部编辑单元；AI 编辑可以作用到一页，部分版本也支持整份修改。
Style 不只是换颜色，还会影响排版和写作语气；图片位置、overlay、对齐方式是显式控制项。
Gamma 的 card 可以随内容动态伸缩，这很适合网页展示；但导出固定 16:9 PowerPoint 时，仍需要更
严格的尺寸约束。
2.2 Cursor：Harness 是上下文、工具和反馈循环
Cursor 不负责生成 PPT，但它的 Agent Harness 思路很有参考价值：
用户目标
  -> 读取相关上下文
  -> Plan / Todo
  -> 调用搜索、编辑、终端等工具
  -> 检查实际结果
  -> 修错并继续
  -> Checkpoint / Review
我主要借鉴了这些能力：
Rules 保存长期、可复用的约束；Skills 按任务动态加载流程，避免所有信息一直塞进上下文。
Plan/Todo 把长任务拆开，并实时显示当前进度。

3. 设计思路
3.1 先确认大纲，避免把返工推到最后
如果模型直接生成六页 PPT，用户最后才发现叙事顺序不对，所有视觉和排版都要重做。因此入口统一变
成：
主题  / 任意文本  / 空输入
  -> 可编辑大纲
  -> 结构契约与逻辑审查
  -> 用户明确确认
  -> 才允许生成  PPT
空输入也会得到可编辑大纲；已有材料则尽量忠实提炼。divergence 控制事实之外可以发散多少，
content_richness 单独控制正文要点数量和解释深度，避免“想让内容更丰富”被误解成“可以编更多事
实”。
这一块由于会将全部内容传给 LLM 进行规划，因此材料文本的形式可以很多样，用户可以在材料里面记录零
零散散的想法，最终会汇总成结构化的大纲。


===== PAGE 7 =====
第 7 页PPT Generator Harness · 开发复盘
3.2 模型负责语义判断，Harness 负责可验证的边界
模型适合做：传播目标、叙事结构、视觉隐喻、内容重写、是否需要图片。
确定性代码适合做：页数、ID、确认门、HTML 安全、文本是否丢失、坐标越界、字号下限、文件版本、
PPTX 编译和重试上限。
这条分工很关键：如果让模型自己判断“我生成的页面是否合法”，它很容易在同一个错误上反复改；如果全
部写成固定模板，又失去了 AI 的表达能力。
3.3 视觉方案和视觉实现拆成两次调用
早期只让模型直接写 HTML/CSS，页面虽然能渲染，但经常没有明确的图形语言，也不会主动申请图片。后
来拆成两阶段：
1. VisualLanguagePlan：先回答这一页要传达什么、用什么构图、图形、色彩、素材和跨页承接。
2. VisualSlideDesign：再按已经批准的方案生成 HTML/CSS。
视觉方案的核心字段包括：
communication_goal
visual_thesis
layout_family
composition
information_hierarchy
graphic_elements
asset_strategy / asset_requests
color_strategy / typography_strategy
continuity / avoid
这样 UI 能在 HTML 还没写完时先显示“模型准备怎么做”，也能判断后续 HTML 有没有偏离原方案。
这样能让用户溯源，判断模型设计是否合理，也方便精细地微调。

3.4 HTML/CSS 是中间视觉语言，DeckIR 是状态真相
模型擅长写 HTML/CSS，也容易表达不规则构图、渐变、遮罩和 SVG。Chromium 又能给出真实 DOM 边
界，所以 HTML/CSS 很适合作为视觉草稿语言。
但不能把 HTML 当唯一状态。系统仍用 DeckIR 保存页面、元素、稳定 ID、内容、视觉方案、素材、版本和
验证结果。局部修改走 PatchSet。
3.5 视觉保真和 PowerPoint 可编辑性同时保留
最终转换采用混合策略：
HTML 的非文本视觉层渲染为背景，保留复杂视觉效果。
带 data-ppt-kind="text" 和唯一 data-role 的语义文本转换成 PowerPoint 原生文本框。
data-ppt-source-id 把视觉节点映射回大纲锁定内容。

5. 核心 Harness 怎么工作
5.1 大纲 Harness
这一层主要用于评估“六页内容连起来是不是一个完整故事”。 在实际使用中容易发现 LLM 在生成大纲的时
候不同页之间的逻辑联系有时候比较混乱。 普通结构校验只能发现少页、缺封面之类的硬错误；因此这里额
外做了一套独立的全局叙事逻辑审查，在用户确认大纲前先检查传播任务、相邻页承接和结论是否成立。
整个流程是：
用户需求
  -> AI 生成  OutlineProposal
  -> 确定性结构契约
  -> 独立  AI Logic Reviewer
       -> 通过：把审查报告和大纲一起展示给用户
       -> 不通过：按  revision_brief 重写完整大纲
                    -> 再过结构契约
                    -> 再做一轮  Logic Review
  -> 用户编辑、复审和确认
这里有三道不同性质的控制：
1. 生成 Prompt 和 Pydantic Schema：要求模型返回标题、传播任务以及逐页的 semantic_type / title
/ purpose / key_points，先把自由文本收敛成可检查对象。
2. 确定性结构契约：检查目标页数、第一页必须是封面、最后一页必须是总结，以及中间页类型是否合法。
这些规则不交给模型判断；进入可编辑草稿后再分配稳定 ID，后续内容扩写必须原样返回这些 ID，不能
偷偷增删或调换页面。
3. 独立逻辑 Review：使用另一个 Prompt 和输出 Schema 阅读整份大纲，而不是让生成模型顺手评价自
己。它必须回答下面五类问题：
评分维度 实际检查的问题
narrative_arc 整份内容是否围绕传播任务形成“背景/问题 -> 判断 -> 方法/
证据 -> 行动”的推进，而不是页面并列堆砌？
adjacent_continuity 第 1->2、2->3 等每一对相邻页面是否有明确承接，有没有突
然换话题？
audience_alignment 标题、论据和行动建议是否适合目标受众，而不是一套泛化文
案？
redundancy_control 页面之间是否重复表达同一个观点，或者某一页没有独立叙事
任务？
conclusion_support 总结和行动建议是否由前文支撑，而不是最后突然喊口号？

===== PAGE 12 =====
第 12 页PPT Generator Harness · 开发复盘
Review 返回每项分数、每一对相邻页的承接判断、带页码和严重级别的问题、修改建议，以及可直接交给整
改模型的 revision_brief。当前默认通过策略比较严格：总分至少 75；五项中任何一项不得低于 60；所有
相邻页都必须判定为连贯；不能存在 warning/error 级阻塞问题。
逻辑审查自己也要过 Harness
模型有可能漏评某一对页面，或者给了高分却同时报告严重问题，因此不能直接相信 Reviewer 的一个
passed。代码会再次确定性检查评审结果：
五个必需维度是否全部给分；
是否恰好覆盖 1->2 ... N-1->N 的全部相邻关系；
是否出现重复关系、越界页码或重复 rule_id；
分数、相邻页判断和问题严重级别是否同时满足通过策略。
只有这些条件共同成立，状态才会变成 passed 或 passed_with_suggestions。否则统一进入
needs_revision，避免模型用一个好看的总分绕过具体问题。
有界地重写并复审
未达标时，Repair Prompt 会拿到原始需求、当前完整大纲和结构化审查报告，返回一份完整的
OutlineProposal。整改稿必须保持页数、封面/总结边界和允许的中间页类型；原有逐页视觉要求也会保
留。若结构契约被破坏，自动整改立即停止，不会把错误大纲继续传给后续 PPT 流程。
默认最多整改 2 轮，也就是最多经历 3 次审查。下一轮会带上上一轮结果，并通过稳定 rule_id 计算
revision_delta：哪些问题已经解决、哪些仍存在、哪些是本轮新引入的，以及总分变化。这样能看出整改
是否真正收敛，而不是只看到“又生成了一版”。所有 Review/Repair Prompt、结构化输出、轮次、错误和
耗时也都进入 Prompt 历史与实时进度日志。

5.2 Browser Harness
HTML/CSS 返回后，先检查源代码，再在 1600x900 Chromium 画布中实测：
禁止 script、iframe、表单、事件处理器、外部 URL 和 CSS import。
每个可见文本必须是受管节点，并有唯一 role。
标题和大纲锁定内容不能丢失或被改写。
检查字号、越界、scroll overflow、文本互相重叠、文本压住图片且没有可读性保护。
图形容器、素材引用和 data-ppt-source-id 必须满足契约。

    A["HTML/CSS 初稿 "] --> B[" 确定性  HTML Contract Patch"]
    B --> C["Chromium 实测 "]
    C -- 通过  --> D["DOM 转  DeckIR"]
    C -- 几何 / 字号问题  --> E["role 级  CSS Patch ，最多  3 轮 "] --> C
    C -- 结构问题或  Patch 不收敛  --> F["AI Repair / Redesign ，最多  3 轮 "] --> C
    C -- 仍失败  --> G["auto 模式才允许整页  fallback ； ai 模式直接报错 "]
这里不把 fallback 当普通路径。保留原视觉页优先，只有确定性 Patch 和有限 AI 重设计都失败时才降级。
5.3 素材 Harness
视觉规划器可以请求 photo、illustration、texture 或 icon。系统随后：
1. 从用户素材库、Openverse、Unsplash、Pexels 或 Iconify 搜索候选。
2. 先用标题和标签敏感词做元数据拦截。
3. 下载到本地，检查格式、大小、许可和来源。
4. 视觉模型判断内容安全性与页面相关性。
5. 审核不可用时默认禁止采用；用户只能显式点击“跳过视觉审核并采用（风险自担）”。
6. 记录 provider、作者、来源、许可和审核原因，并写入 speaker notes。
人工换图不再重新请求模型写一遍 HTML。只要原页面保留了素材 slot，就复用 HTML/CSS 和可编辑文字几
何，替换本地图片后重渲染受影响页，再验收整份 PPT。

5.4 PowerPoint Harness
浏览器通过不等于 PPT 通过。Chrome 和 PowerPoint 的字体度量、换行、TextFrame margin 和组合对象
行为并不一致，所以还要：
生成  PPTX
  -> Microsoft PowerPoint COM 导出  PNG/PDF
  -> 读取真实文本边界
  -> 验证重叠、越界、 overflow
  -> 首轮优先翻译为局部  CSS Patch
  -> 必要时  AI 根据  PowerPoint 测量重设计
  -> 最后做有界、单调的  DeckIR 几何修复
  -> 重新编译与复验
一旦 DeckIR 已经按 PowerPoint 测量扩过文本框，就不再从 HTML 重建这批几何，避免“HTML 修一次、
PPT 又还原一次”的振荡。

5.5.1 逐页、流式的进度模型
视觉方案和 HTML/CSS 生成允许最多三页并行，但 Browser Harness 保持单消费者。任意一批 HTML/CSS
返回后就进入 Harness 就绪队列，不再等待所有页面的模型调用全部结束。这样在后续页面仍由 LLM 生成
时，先返回的页面已经可以执行 HTML Contract Patch、浏览器渲染、局部 CSS Patch 和预览发布。
P1/P2/P3 并行请求  HTML/CSS
  ├─ P1 先返回  -> 保存  HTML 调试预览  -> Contract Patch -> Browser Harness
  ├─ P2 继续由  LLM 生成
  └─ P3 返回后进入  Harness 等待队列
P1 Harness 通过
  -> 保存  P1 checkpoint
  -> 发布  P1 实时预览
  -> 单消费者继续检查已经就绪的  P3 或  P2
5.5.2 Checkpoint 与局部重试
每当视觉方案、HTML/CSS 或完整页面形成可复用结果时，系统都会更新构建 checkpoint，保存：
DeckIR 当前版本和已经通过 Harness 的页面 ID。
已经返回、但尚未完成 Harness 的视觉方案与 HTML/CSS。
失败页 ID、页码、标题、失败阶段、错误原因和重试次数。
已完成页面的预览路径，以及未完成页面可以复用的模型结果。
某页失败时，服务抛出带恢复信息的单页错误，用户点击“重试该页”后，流程为：
载入  checkpoint
  -> 保留已通过页面的内容、 HTML/CSS 、 DeckIR 几何和预览
  -> 复用或按需更新失败页的视觉方案，并强制重新请求该页  HTML/CSS
  -> 复用其他未完成页中已经返回的模型结果
  -> 继续剩余页面的  Contract Patch 与  Browser Harness
  -> 所有页面就绪后重新编译整份  PPTX
  -> 再跑整份  PowerPoint 渲染与验收
因此“局部重试”只缩小重新生成的范围，不会降低最终验收范围。已经完成的页面不会因为第三页失败而重
新请求 LLM；但是修好的第三页加入 DeckIR 后，整份 PPT 仍要重新检查跨页结构、PowerPoint 文本边
界、重叠和越界。这样既避免全部重做，也避免“单页看起来没问题，但合回整份 PPT 后出错”。

7. 开发过程遇到过的问题
7.1 从线性生成器变成 Agent Loop
第一版思路接近：输入 -> 大纲 -> 固定布局 -> PPTX -> 验证。它能跑，但用户无法在关键节点介入，失败
也不知道发生在哪。
后续逐步增加了：大纲确认门、独立逻辑审查、逐页视觉方案、Prompt 历史、Trace、Browser Harness、
PowerPoint 实测、checkpoint 和局部编辑。系统才从“生成脚本”变成 Harness。
7.2 CSS 怎么修都不好的页面，其实是 HTML 结构错了
典型错误包括 missing_locked_text 和 missing_graphic_container。CSS 只能调整已有节点的样式，不能
凭空恢复丢失的锁定文本，也不应该猜哪个外层容器才是真正图形容器。
修复方式：
增加确定性 HTML Contract Patch，补唯一 role、锁定标题契约、素材 slot 和 graphic 标注。
CSS 多轮不收敛时，把 issue history 交给 redesign_slide，明确丢弃旧 DOM 与几何，但保留锁定内
容、素材和主题。
增加回归测试，防止模型修复后再次破坏 HTML 契约。
7.3 浏览器看起来正常，PowerPoint 仍然溢出或错位
一开始验证器固定扣除一段假想的文本框空间，导致本来没溢出的内容被误报；同时 PowerPoint 的真实
TextFrame margin、中文换行和字体基线又确实和浏览器不同。
修复方式：
移除固定扣除 8pt 的逻辑，读取真实 TextFrame margin。
优先扩展文本框到安全空白，而不是持续缩小字体。
标题框因 PowerPoint 字体度量需要增高时，如果顶部有空间，就向上扩展并保持下边界不动，避免把下
面整组内容推离背景。
圆形编号使用与背景圆圈完全一致的 DOM 视觉盒做水平/垂直居中，不再靠经验值额外上提。
这里最后还暴露过一个很典型的“双层几何”问题：修复器为了避开标题，把副标题和后面 10 个可编辑文本
框整体下移了约 0.11in，但圆圈属于已经栅格化的背景，没有一起移动，于是第 6 页的数字跑出了圆心。此
时不应该继续给数字加偏移量，而应该让标题框向上扩展，从源头避免移动时间线。这个例子也说明，
PowerPoint 修复不能只看文本框是否合法，还要检查它是否仍与背景视觉单元对齐。

A.8 PromptRecord 与可追踪性
每次结构化模型调用都会保存以下信息：
stage、模型名称和 Prompt ID。
完整 System Prompt 与 User Prompt。
Pydantic response_schema。
结构化 parsed_response。
尝试次数、调用模式、耗时和状态。
每次失败的异常摘要，以及最终是否使用 JSON/text fallback。
图片附件的文件名和用途摘要；不把图片二进制直接复制进文档。
因此，本附录回答“系统设计时采用了什么 Prompt”，Prompt 历史回答“某一次真实任务到底向模型发送
了什么、返回了什么以及为什么重试”。两者共同构成可复现实验记录。
