# 面试讲解：我是怎样搭出 PPT Agent Harness 的

## 30 秒版本

我没有从“让模型写 python-pptx”开始，而是先拆解 Claude Code、Codex 和 OpenCode
背后的 harness：模型循环只是中心的一小块，真正决定可靠性的还有工具定义、权限、
项目上下文、错误恢复、压缩和验证。我把这些通用能力做成核心，再把 PPT 做成垂直
工具包，形成“理解现有文件—按语义版式修改—结构验证—真实 PowerPoint 渲染—根据
证据修复”的闭环。最后用固定测试集与真实渲染验证，而不是只看文件成功生成。

## 五分钟版本

### 1. 先定义问题

用户需求不是单纯生成 PPT，还包括修改已有 deck、保持风格、重排密集内容、避免裁切、
保存为可编辑文件。因此成功标准至少包含内容正确、文件有效、版式可读和修改可追踪。

### 2. 调研竞品并区分事实与推断

我从 Codex 源码看执行沙箱、精确 patch、并行工具和 compaction；从 OpenCode 看
session、permission 和 plugin/compaction 生命周期；从 Claude Code 的公开接口与行为
推断 hooks、skills、plan mode 和 subagent。竞品展示经常省略权限、渲染和失败恢复，
我把这些隐含层显式补回设计。

### 3. 搭通用 harness

循环维护完整 tool-call 对应关系；工作区做真正的路径包含判断；命令分 allow/ask/deny；
工具参数按 schema 校验；只读调用可并行；暂态 API 错误有限重试；任务、修改文件、失败
指纹和验证证据进入结构化状态；上下文过长时保留这份状态而不是盲目 FIFO 截断。

### 4. 搭 PPT 垂直闭环

我提供创建/加载 deck、shape inventory、按 shape ID 修改、封面/正文/比较/指标卡/表格/
图片等语义版式。保存后先做 OOXML 与几何检查，再调用本机 PowerPoint 渲染 PNG。
第一版虽然结构检查通过，但渲染后发现空白过多、页面同构，于是新增指标卡和表格布局；
第二次渲染显示信息层级和密度明显改善。这次“渲染—发现问题—修改—再渲染”是项目中
最有说服力的证据链。

### 5. 评测与诚实边界

本地测试证明的是实现正确，不等于超过 Claude Code/Codex。要比较 Terminal-Bench 或
SWE-bench Verified，必须固定同一模型、数据集版本、容器、预算和重试策略，报告成功率、
成本、耗时和置信区间。我先用离线测试和 fake provider 消除确定性问题，最后才花少量
DeepSeek 额度做冒烟和小样本，避免把钱浪费在明显的工程 bug 上。

## 面试官可能追问

**为什么不直接用 MCTS？** 代码动作空间巨大、验证昂贵且副作用多。只有失败、候选分歧
或高风险动作才值得预算化分支；普通步骤走单轨 + 确定性验证更省成本。

**为什么插件比把所有工具塞进 prompt 好？** 工具越多，选择错误和 token 成本越高。
元数据常驻、正文与工具按需加载，既保留扩展性又减少干扰。

**如何证明 PPT 好看？** 不能只用字符数代理。必须实际渲染，再做人工盲评或视觉模型
评估，同时保留确定性的裁切、越界、重叠和内容完整性检查。

**最难的 bug 是什么？** “验证通过但视觉很差”。这促使我把结构验证与 render QA 分层，
也说明 harness 的价值不是多一次模型调用，而是把正确反馈在正确时间送回循环。
